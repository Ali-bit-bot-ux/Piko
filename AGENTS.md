# AGENTS.md — Piko

Правила для ИИ-агентов (Claude Code и других) в этом репозитории. Язык общения с командой: русский. Код, имена и комментарии: английский.

## Порядок чтения (в начале каждой сессии)
1. Этот файл.
2. `PROGRESS.md`: что сделано, что дальше.
3. `TASKS.md`: взять **одну** задачу, у которой все зависимости `done`.
4. По необходимости: `docs/product.md` (что строим), `docs/design.md` (как выглядит), `docs/architecture.md` (как устроено), `docs/decisions.md` (что уже решено), `docs/scoring.md` (модель оценки), `docs/event-log.md` (журнал событий), `docs/pricing.md` (тарифы).

Не полагаться на память чата: всё важное записано в этих файлах. Не знаешь, где что, смотри сюда.

## Что такое Piko
Платформа честного и понятного отбора в футбольные академии (Казахстан): набор → регистрация детей по QR → испытания → оценка 0–100 по единым критериям → отчёт родителю. ИИ-анализ видео и событий делает оценку объективной. Подробнее: `docs/product.md`.

## Стек
Next.js (App Router) + TypeScript, один репозиторий. Подтверждено: Tailwind CSS, Postgres + Prisma, Auth.js, zod, Vitest, Playwright (D-007..D-011 в `docs/decisions.md`). Всё со статусом `предложено` не использовать, пока команда не подтвердила.

## Структура
Целевая структура в `docs/architecture.md`. Новые папки верхнего уровня без решения не создавать.

## Главные правила
1. **Внешние сервисы только через интерфейсы.** `AnalysisProvider`, `Storage`. Страницы и компоненты не импортируют SDK модели или облака напрямую.
2. **Строгие схемы.** Ответ модели, формы и API валидируются zod. Невалидное это ошибка, а не «показать как есть».
3. **Секреты только в `.env.local`.** Не коммитить ключи. При добавлении переменной обновить `.env.example`.
4. **Данные детей.** Видео, имена, оценки несовершеннолетних — персональные данные. Хранить минимум, не логировать имена и содержимое видео, не отправлять никому кроме выбранного провайдера анализа. Согласие родителей при регистрации обязательно. Публичные отчёты: неугадываемый токен, срок жизни, `noindex`. Видео удаляются после завершения набора и отправки отчётов родителям (D-020).
5. **Доступ.** Каждый запрос к данным проверяет на сервере роль и принадлежность к Organization. В страницах и серверных действиях вызывать `requireStaff()` (`src/server/auth/session.ts`), в слое данных брать только функции вида `findIntakeForUser(user, id)` (`src/server/db/`), которые сами фильтруют по организации. Читать сессию можно только внутри `<Suspense>` (cacheComponents). `src/proxy.ts` лишь быстрая проверка cookie, не защита (D-025).
6. **Стоимость.** Лимитировать число кадров и размер запроса к модели, считать токены и стоимость.
7. **Оценка ИИ не окончательна.** Тренер может скорректировать, обоснование видно.
8. **Не выдумывать факты.** Реальные логотипы, «50+ академий», отзывы и цифры с референса не публиковать без подтверждения (D-013). Использовать заглушки.
9. **Дизайн.** Mobile-first, дружелюбно, интуитивно, доступно. Сверяться с `docs/design.md`. Референс `docs/reference/landing.webp` — фейковый набросок: брать только дизайн, расположение кнопок и информации (D-018), содержание (тексты, цифры, критерии) только из `docs/`. Цены на сайте пока заглушки (D-021). После вёрстки страницы запускать скилл `web-design-guidelines`.
10. **Хуки плагина не включать** (D-012). Исходящие действия (push, отправка писем и сообщений, публикация) только по явному слову владельца.
11. **Тексты интерфейса только из словаря.** Не хардкодить русские строки в компонентах и страницах: добавлять в `src/lib/i18n/dictionaries/ru.ts`, читать через `getDictionary()` и `interpolate()` (D-022). Исключение: страница `/dev/ui` (только для разработки). Казахские тексты не придумывать, их даёт владелец.

## Как работать
- Одна задача за раз. Для нетривиальных сначала план (`/ali plan <задача>`), затем реализация (`/ali tdd` для логики, например `scoring`).
- Маленькие шаги, которые можно проверить. После шага запускать `lint`, `typecheck`, `test`.
- Перед завершением: `/ali verify`, `/ali code-review`.
- Новая зависимость только при необходимости, причину записать в `PROGRESS.md`.
- Изменение архитектуры или стека: сначала запись в `docs/decisions.md`, затем код.
- Не удалять и не перезаписывать чужие файлы без явной просьбы. Git: небольшие коммиты, ветка на задачу (`t-001-scaffold`).

## Завершение задачи (обязательно)
1. В `TASKS.md` поставить статус `done` (или `blocked` с причиной).
2. Добавить запись сверху `PROGRESS.md` по шаблону.
3. Если принято решение, добавить в `docs/decisions.md`.
4. Если упёрся в неизвестное, записать в «Открытые вопросы» (`TASKS.md`) и спросить владельца, а не гадать.

## Скиллы проекта (`.claude/skills/`)
- `web-design-guidelines`: проверка интерфейса (доступность, формы, UX). Скачивает актуальные правила из репозитория Vercel при запуске.
- `react-best-practices`: производительность React и Next.js.
- `composition-patterns`: архитектура компонентов.

## Команды
- установка: `npm install`; переменные окружения: скопировать `.env.example` в `.env.local`
- разработка: `npm run dev`
- проверка: `npm run lint`, `npm run typecheck`, `npm test`, `npm run format:check`
- сборка: `npm run build`
- тесты: `npm run test:watch`, `npm run test:coverage` (порог 80% для `src/server` и `src/lib`)
- форматирование: `npm run format` (Prettier, только `src` и `tests`)
- база данных (Postgres, `DATABASE_URL` в `.env.local`): `npm run db:migrate` (новая миграция после правки `prisma/schema.prisma`), `npm run db:deploy`, `npm run db:seed` (демо-данные, можно запускать повторно), `npm run db:generate`, `npm run db:validate`. Клиент: `getPrisma()` из `src/server/db/client.ts`. Интеграционные тесты БД пропускаются, если `DATABASE_URL` не задан.
